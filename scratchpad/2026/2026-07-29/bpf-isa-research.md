# BPF ISA: the spec, the tooling, and the unspecified remainder

Question: what is the actual standardization status of the BPF ISA as of mid-2026, what tooling exists around it, and where are the gaps — especially the ones relevant to wire-format spec work, conformance testing, and IR design?

Method: deep-research run (2026-07-29). 6 parallel research threads (spec/governance, toolchain, formal methods, conformance/runtimes, companion formats, MLIR angle) over ~90 primary sources (IETF datatracker, IANA, kernel source/docs, LLVM/GCC/binutils source and docs, GitHub repos, LWN, papers). 23 load-bearing claims then adversarially cross-checked against primary sources, one verifier per claim; ✓ marks cross-checked claims. Uncrossed claims rest on the thread agents' primary-source citations.

## Headlines

1. **The ISA has a real spec** — RFC 9669, Proposed Standard, October 2024 — but it froze a snapshot, and the kernel has since shipped four instruction families that exist in no spec and no registry.
2. **The standardization machinery is stalled**: the IETF BPF WG has not met since July 2024, none of its five remaining chartered deliverables has an adopted draft, and the IANA instruction registry has not been touched since November 2024.
3. **The de facto spec is distributed across implementations**: libbpf (ELF/BTF/CO-RE), the kernel verifier (safety), bpf_conformance (runtime semantics), LLVM (assembly syntax). Each is authoritative by adoption, none by document.
4. **Formal methods cover every pipeline stage except two**: LLVM IR → BPF translation validation does not exist, and no mechanized semantics covers the standardized dialect (every formal model targets rBPF, Solana sBPF, or a frozen 2020-era subset).
5. **No MLIR or xDSL dialect for BPF exists anywhere** — not even an abandoned prototype.

## The spec: RFC 9669

- Proposed Standard, IETF stream, October 2024; the BPF WG's only RFC. Two encodings (64-bit basic, 128-bit wide), 8 instruction classes. ✓ [RFC 9669](https://www.rfc-editor.org/rfc/rfc9669.html), [datatracker](https://datatracker.ietf.org/doc/rfc9669/)
- Seven conformance groups instead of version numbers: base32 ⊂ base64, atomic32 ⊂ atomic64, divmul32 ⊂ divmul64, plus deprecated `packet`. Edge cases standardized as runtime (not verifier) behavior: div-by-zero → dst=0, mod-by-zero → dst unchanged, shifts masked by 0x3F/0x1F. [RFC 9669](https://www.rfc-editor.org/rfc/rfc9669.html)
- Extension rule: registered conformance groups are immutable — new instructions require a *new* group including the old one. ✓ [RFC 9669](https://www.rfc-editor.org/rfc/rfc9669.html)
- Explicitly out of scope: verifier behavior, psABI/calling conventions, helpers, maps, program types, and BTF ("standardization is left for future work"). [RFC 9669](https://www.rfc-editor.org/rfc/rfc9669.html)

## Spec vs. reality: drift and governance

- The WG is nominally Active but dormant: no sessions since IETF 120 (2024-07); charter deliverables beyond the ISA (verifier expectations, BTF, psABI guidance, maps/helpers, architecture) have zero adopted drafts. ✓ [WG meetings](https://datatracker.ietf.org/group/bpf/meetings/), [charter](https://datatracker.ietf.org/wg/bpf/about/), [WG docs](https://datatracker.ietf.org/wg/bpf/documents/)
- The IANA "BPF Instruction Set" registry: last updated 2024-11-22, every entry cites RFC 9669 only. ✓ [IANA registry](https://www.iana.org/assignments/bpf-instructions/bpf-instructions.xhtml)
- Meanwhile the kernel shipped, post-snapshot: **may_goto** (BPF_JCOND 0xe0, bounded-loop escape hatch, Linux 6.9), **addr_space_cast** (arena address spaces, 6.9), **load-acquire/store-release** (BPF_LOAD_ACQ 0x100 / BPF_STORE_REL 0x110 as BPF_ATOMIC imm values, 8/16/32/64-bit, Linux 6.15) ✓, and **indirect jumps** (`gotox` + instruction-array map type, Linux 6.19, 2026-02) ✓. [bpf.h](https://github.com/torvalds/linux/blob/master/include/uapi/linux/bpf.h), [LWN on jump tables](https://lwn.net/Articles/1042703/), [LPC 2025 acq/rel talk](https://lpc.events/event/19/contributions/2163/attachments/1806/3886/Introduction%20to%20eBPF%20Load-Acquire%20and%20Store-Release%20Instructions.pdf)
- None of these appears in the kernel's own standardization doc (`instruction-set.rst`) — 2025 commits are wording fixes only. [kernel doc](https://docs.kernel.org/bpf/standardization/instruction-set.html), [commit log](https://github.com/torvalds/linux/commits/master/Documentation/bpf/standardization/instruction-set.rst)
- The extension process was exercised for the first time in May 2026 and immediately hit friction: a doc patch adding acq/rel to instruction-set.rst extended atomic32/atomic64 in place, and a WG chair — supportive of the addition itself — flagged that as violating the RFC's group-immutability rule ("you can't just add them to the existing one"), steering toward a new conformance group instead. Still unmerged as of July 2026. ✓ [ietf bpf thread](https://mailarchive.ietf.org/arch/msg/bpf/d1GUUmfXTM8SN8X2wlO1nTbYtaE/)
- LLVM declined a v5: acq/rel was proposed under `-mcpu=v5`, re-gated under v4; gotox likewise landed under v4 with reviewers noting version proliferation doesn't scale. v4 is now a rolling bucket with per-feature disable flags — cumulative cpu versions and orthogonal RFC conformance groups describe the same ISA and match neither each other nor the shipped instruction set. ✓ [PR #108636](https://github.com/llvm/llvm-project/pull/108636), [PR #149715](https://github.com/llvm/llvm-project/pull/149715), [BPFSubtarget.cpp](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/BPF/BPFSubtarget.cpp)
- De facto opcode governance: bpf-next maintainer review with LLVM co-design; new instructions mostly reuse existing classes (gotox = JA|X, acq/rel = new ATOMIC imm values) rather than claim new opcodes. No documented post-RFC extension pipeline; no evidence of any IANA registration request. [bpf.h](https://github.com/torvalds/linux/blob/master/include/uapi/linux/bpf.h)

## Toolchain

- **LLVM**: full backend since 2015; maintainers per Maintainers.md: Yonghong Song, Eduard Zingerman ✓. Default `-mcpu` moved v1→v3 in Clang 20 ✓. BTF/`.BTF.ext` emitted directly with `-g` on the bpf target. [Maintainers.md](https://github.com/llvm/llvm-project/blob/main/llvm/Maintainers.md), [BTF doc](https://docs.kernel.org/bpf/btf.html)
- **GCC**: port merged in GCC 10 (2020); defaults `-mcpu=v4` and `-masm=pseudoc` ✓. As of GCC 16 (2026-04): same BTF type/decl tags as Clang modulo one DWARF-forced identifier difference; CO-RE pragma support; passes 601/713 kernel BPF selftests ✓; Gentoo offers GCC as an optional (not default) BPF compiler — a claim the LWN article itself corrected in a footnote. Remaining gaps: no verifier-friendly codegen strategy (a `-fverifiable` flag was floated), binutils lacks BTF linking. [GCC eBPF options](https://gcc.gnu.org/onlinedocs/gcc/eBPF-Options.html), [LWN GCC 16](https://lwn.net/Articles/1071973/), [LWN Cauldron 2025](https://lwn.net/Articles/1039827/)
- Verifier-friendliness as a compiler concern is acknowledged but mostly unimplemented on both toolchains (LSFMM+BPF 2024 discussion: PREVAIL-in-compiler, pass control, branch-hint preservation). [LWN](https://lwn.net/Articles/974945/)

## Assembly formats

Three dialect families, none with a published grammar; RFC 9669 standardizes encodings, not text. ✓ (no-grammar claim cross-checked for pseudo-C)

- **Pseudo-C** (`r0 = *(u32 *)(r1 + 0)`): the only syntax LLVM implements (clang inline asm, llvm-mc, llvm-objdump); kernel verifier logs and selftests (inline asm in `__naked` functions) use it; GAS accepts it since binutils 2.41 (2023, auto-detected and mixable with normal syntax — added explicitly for LLVM compatibility); the explicit `-mdialect=pseudoc` flag and objdump's `-M pseudoc` arrived in 2.42 (2024). ✓ (version split corrected by verifier) [GAS pseudo-C docs](https://sourceware.org/binutils/docs-2.41/as/BPF-Pseudo_002dC-Syntax.html), [binutils bug 29728](https://lists.gnu.org/archive/html/bug-binutils/2022-10/msg00161.html)
- **GAS "normal"** (`add32 %r0, 1`): binutils default; GCC emits it or pseudo-C; no uptake beyond the GNU toolchain. [GAS BPF instructions](https://sourceware.org/binutils/docs/as/BPF-Instructions.html)
- **Bare-mnemonic** (`mov32 r0, 1` / `mov32 %r0, 1`): uBPF's Python assembler, rbpf's Rust assembler, and bpf_conformance's C++ assembler (%-prefixed variant) — the dialect of the conformance corpus, parsed by nothing in either mainline toolchain. [uBPF](https://github.com/iovisor/ubpf), [bpf_conformance tests](https://github.com/Alan-Jowett/bpf_conformance/tree/main/tests)
- Interop is by convergence, not spec: GAS aligned its `;`-comment behavior to clang in 2.42; GAS is more permissive than clang in known edge cases and can mix dialects in one file; LLVM cannot parse GAS normal syntax at all. No cross-toolchain round-trip test suite exists; whether llvm-objdump output reassembles under GAS is untested territory. [binutils bug 29728](https://lists.gnu.org/archive/html/bug-binutils/2022-10/msg00161.html)

## Conformance and runtimes

- **bpf_conformance** is the de facto executable spec: 313 `.data` tests (asm + memory in, r0 out) run by plugin processes; kernel "treated as the authoritative eBPF implementation." Test corpus descends from uBPF's suite (Big Switch copyright headers); a parallel `rfc9669_*` series ties tests to RFC text; the library filters by cpu version (v1–v4) and RFC conformance-group names (plus non-RFC `callx`). ✓ [repo](https://github.com/Alan-Jowett/bpf_conformance), [API header](https://github.com/Alan-Jowett/bpf_conformance/blob/main/lib/include/bpf_conformance_core/bpf_conformance.h)
- CI adoption: uBPF (submodule, every test × JIT/interpreter/safe-interpreter) ✓, eBPF for Windows (bpf2c job) ✓, PREVAIL, llvmbpf ("Passed 313 out of 313") ✓. [ubpf CMake](https://github.com/iovisor/ubpf/blob/main/ubpf_plugin/CMakeLists.txt), [e4w CI](https://github.com/microsoft/ebpf-for-windows/blob/main/.github/workflows/cicd.yml), [llvmbpf results](https://eunomia-bpf.github.io/llvmbpf/bpf_conformance_results.txt)
- Open conformance question: undefined-opcode handling — the spec gives no guidance on what runtimes must do; flagged at LSF/MM/BPF with no resolution. [eBPF Foundation recap](https://ebpf.foundation/linux-storage-filesystems-mm-and-bpf-summit-recap-and-video-bpf-conformance-handling-undefined-opcodes/)
- Runtime ISA fidelity varies widely: DPDK librte_bpf stops at ~v2 (no JMP32, no fetch atomics, no v4) [DPDK guide](https://doc.dpdk.org/guides/prog_guide/bpf_lib.html); rbpf documents missing instructions and error-`Result` semantics where the kernel defines silent values [rbpf](https://github.com/qmonnet/rbpf); eBPF for Windows publishes a per-instruction support matrix [isa-support.rst](https://github.com/microsoft/ebpf-for-windows/blob/main/docs/isa-support.rst).
- Divergences are real, not theoretical: bpf2c shipped wrong shift-mask semantics (issue #2465) ✓; BpfChecker (CCS 2024) differentially fuzzed three runtimes — Solana rbpf, qmonnet rbpf, and Windows eBPF — finding 28 new flaws (two CVEs, with fixes also landing in uBPF and PREVAIL), JIT-vs-interpreter sign-extension mismatches among the divergence classes ✓ (count and target list corrected by verifier). [e4w #2465](https://github.com/microsoft/ebpf-for-windows/issues/2465), [BpfChecker](https://dl.acm.org/doi/10.1145/3658644.3690237), [trophy list](https://gist.github.com/bpfchecker/34a31c23a2da08564577df1bc8d8fce8)
- The Solana fork is reconverging: SIMD-0377 ("eBPF ISA compatibility," merged into the SIMD repo 2026-01, status Review) aligns sBPF with the v3-level ISA — adding JMP32, reverting the nonstandard callx encoding — explicitly so stock LLVM can target it. A dialect fork paying its way back to the standard. ✓ [SIMD-0377](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0377-ebpf-isa-compatibility.md)

## The unspecified remainder: BTF, ELF, memory model

- **BTF**: spec-like coverage only in `Documentation/bpf/btf.rst` (encoding, 19 kinds); deduplication — required to produce vmlinux BTF — is specified only in a maintainer blog post plus libbpf source ✓. RFC 9669 punts BTF explicitly; IETF chartered it as Proposed Standard work, but no draft exists. Six-plus independent implementations (kernel, libbpf, pahole, GCC/binutils, Aya, cilium/ebpf, libbtf). Maintainer testimony on the risk (LWN, May 2026): warning against "three slightly different, separately maintained versions" of dedup, with libbpf's the only one that truly works ✓. [btf.rst](https://docs.kernel.org/bpf/btf.html), [dedup post](https://nakryiko.com/posts/btf-dedup/), [LWN GCC 16](https://lwn.net/Articles/1071973/)
- **CO-RE**: relocation record layout in btf.rst; recording conventions documented as *LLVM behavior* (`llvm_reloc.rst`); the resolution algorithm exists only in libbpf `relo_core.c` and blog posts. Aya's Rust CO-RE has tracked missing compiler intrinsics since 2022. [llvm_reloc](https://docs.kernel.org/bpf/llvm_reloc.html), [aya#349](https://github.com/aya-rs/aya/issues/349)
- **ELF psABI**: the only spec attempt, draft-thaler-bpf-elf-00, expired September 2023, never WG-adopted, no successor ✓. What loaders must implement = what libbpf does; libbpf's section-name table doubles as the ecosystem contract. Documented drift pain: cilium/ebpf mis-tracking libbpf's section-name semantics (#1162); libbpf 1.0's removal of legacy map definitions breaking downstream (Suricata #6250). [draft-thaler-bpf-elf](https://datatracker.ietf.org/doc/draft-thaler-bpf-elf/), [libbpf program types](https://docs.kernel.org/bpf/libbpf/program_types.html), [cilium/ebpf#1162](https://github.com/cilium/ebpf/issues/1162)
- **Memory model**: RFC 9669's atomics are functional-only — no ordering semantics. The 6.15 acq/rel instructions' RCpc (vs arm64 RCsc) semantics were settled in patch review, invisible to any spec. A formal instruction-level model (McKenney + Mohan, herd7/cat, starting from the ARMv8 axiomatic model after judging direct LKMM mapping impractical) was presented in 2024; litmus testing already found real atomics-ordering bugs in weakly-ordered JITs; no bpf.cat has merged ✓. Nothing anywhere states what non-Linux runtimes must guarantee. [LWN 976071](https://lwn.net/Articles/976071/), [acq/rel series](https://lkml.iu.edu/hypermail/linux/kernel/2503.0/03162.html)

## Formal methods coverage map

By pipeline stage:

- **ISA semantics**: mechanized models exist but none covers the standardized dialect — CertrBPF (Coq, CAV 2022; rBPF/RIOT dialect) ✓, Solana sBPF complete semantics (Isabelle/HOL, OOPSLA 2025, validated against the real interpreter) ✓, Jitterbug's Rosette semantics (2020-era Linux ISA), K2's SMT encoding (SIGCOMM 2021 subset). No Sail or K model of any BPF dialect; nothing attached to RFC 9669. [CertrBPF](https://people.rennes.inria.fr/Frederic.Besson/rbpf.pdf), [Solana semantics](https://dl.acm.org/doi/10.1145/3720414)
- **LLVM IR → BPF**: **nothing** — the confirmed gap. Backend translation validation exists for AArch64 (OOPSLA 2025, 46 miscompiles found) and RISC-V (LLVM Dev Mtg 2025), not BPF. ✓ [arm-tv](https://dl.acm.org/doi/10.1145/3763147)
- **Verifier**: fragments only — tnums proofs (CGO 2022), Agni's range-analysis extraction (CAV 2023; kernels 4.14–5.19, 27 new bugs found ✓) and SAS 2024/2025 successors; path-pruning soundness is grant-stage (eBPF Foundation → Rutgers, NSF FMitF). No formal spec of overall verifier semantics; the 2024 NCC audit was manual review. PREVAIL (eBPF for Windows' production verifier) is abstract-interpretation-principled but carries no mechanized soundness proof. [Agni](https://people.cs.rutgers.edu/~sn349/agni/), [PREVAIL](https://github.com/vbpf/prevail), [grants](https://www.prnewswire.com/news-releases/ebpf-foundation-announces-250-000-in-grant-awards-for-five-ebpf-academic-research-projects-302233378.html)
- **JIT (BPF → native)**: Jitterbug (OSDI 2020) verified kernel JITs, contributed a verified RV32 JIT, found 16 bugs ✓ — but predates ISA v4 and everything after; no maintained or CI-integrated verification of current kernel JITs. CertrBPF-JIT (CAV 2024) covers rBPF only; the Solana group has target-side x86-64 semantics (SETTA 2024) with the full JIT proof apparently still in progress. [Jitterbug](https://unsat.cs.washington.edu/projects/jitterbug/)
- **Alternative safety architectures**: VEP (NSDI 2025) — proof-carrying-code path with an in-kernel checker replacing verifier trust; BeePL (2025) — correct-by-compilation typed DSL over CompCert targeting BPF; ePass — compiler-inserted runtime termination budgets; bpfix (2026) — empirical diagnosis of 235 verifier rejections (47% yield only EINVAL). [VEP](https://www.usenix.org/conference/nsdi25/presentation/wu-xiwei), [BeePL](https://arxiv.org/abs/2507.09883), [bpfix](https://arxiv.org/abs/2607.02748)
- **Concurrency**: no formal model connects any of the above — every mechanized ISA semantics is sequential, and the herd7/cat effort is unmerged.

## The MLIR/dialect gap

- No MLIR or xDSL dialect for BPF exists: zero hits across GitHub repo/code search (`EBPFDialect`, `bpf mlir`, etc.), xdslproject/opencompl orgs, LLVM Discourse (one 2025 networking-vision thread mentions eBPF as a possible target; no follow-up), GSoC/LFX listings, arXiv. ✓ [Discourse thread](https://discourse.llvm.org/t/idea-mlir-for-networking-dsp-a-vision-for-a-new-infrastructure-starting-with-a-simulator-poc/88031)
- P4-MLIR lives at `p4lang/p4mlir-incubator` (active, commits through 2026-07): P4HIR dialect modeling P4C's IR; no eBPF lowering path or plans — forward direction is SmartNICs (GSoC 2026 Alkali bridge). The in-tree p4c eBPF backends are in maintenance mode; the active P4→eBPF path is P4TC. [p4mlir-incubator](https://github.com/p4lang/p4mlir-incubator), [p4lang GSoC 2026](https://github.com/p4lang/gsoc/blob/main/program/2026/ideas_list.md)
- Precedents a BPF dialect would build on: SPIR-V (in-dialect binary serialization), WAMI (Wasm dialects preserving structure LLVM loses; ≤7.7% slower than LLVM-based compilers), xDSL RISC-V dialects (CGO 2025: structure-preserving lowering to assembly-level IR, register allocation over structured IR), xdsl-asl (ISA spec language as dialect). Verification tooling: xdsl-smt + "First-Class Verification Dialects for MLIR" (PLDI 2025) — dialect-agnostic translation validation via an SMT dialect. [WAMI](https://arxiv.org/abs/2506.16048), [xDSL RISC-V](https://dl.acm.org/doi/10.1145/3696443.3708952), [PLDI 2025](https://dl.acm.org/doi/10.1145/3729309), [xdsl-smt](https://github.com/opencompl/xdsl-smt)
- bpftrace has no mid-level IR (AST → LLVM IR directly); nothing in the DSL ecosystem occupies the structured-lowering slot. [bpftrace internals](https://github.com/bpftrace/bpftrace/blob/master/docs/internals_development.md)

## Unclaimed territory

Ordered by (leverage × tractability), given the above:

1. **A formal semantics of the RFC 9669 dialect** — every existing model covers someone else's dialect; the standardized ISA, uniquely, has none. Natural substrates: Sail (hardware-adjacent, generates emulators + Isabelle/Coq) or an SMT encoding aligned with bpf_conformance's corpus.
2. **LLVM IR → BPF translation validation** — the arm-tv recipe applied to a far simpler target (no FP, no flags, ~100 instructions); BPF-specific twist: also checking preservation of verifier-acceptability, which semantic refinement alone doesn't capture.
3. **A written grammar + round-trip suite for pseudo-C assembly** — small, unclaimed, immediately useful to both toolchains; the conformance corpus's bare-mnemonic dialect needs a parser bridge to be reusable outside its own runner.
4. **A BPF dialect in MLIR/xDSL** — the niche is confirmed empty; the winning configuration is paired with a structured frontend (parse-graph → verifier-friendly lowering), with xdsl-smt semantics from day one. WAMI is the architectural template.
5. **BTF as a specified wire format** — chartered by IETF, no draft, six implementations, maintainer-acknowledged divergence risk. The single most Pakeles-shaped object in the ecosystem: a load-bearing binary format whose dedup algorithm lives in a blog post.
6. **Memory-model participation** — the herd7/cat effort is early enough that runtime-independent formulation (what must uBPF/Windows/bpftime guarantee?) is still an open framing question nobody owns.

## Verification snapshot

23 load-bearing claims sent to 3 adversarial verifiers against primary sources: 18 confirmed outright, 5 confirmed with corrections applied above (arm-tv bug count 45→46; Gentoo GCC-BPF optional not default; binutils pseudo-C support 2.41 vs flags 2.42; BpfChecker 28 flaws across 3 targets, not 32 across 4; WG-chair acq/rel comment was a procedural not substantive objection). Negative-existence claims (no BPF TV tool, no BPF MLIR/xDSL dialect, no bpf.cat in tools/memory-model, no BTF/psABI drafts) were re-searched independently by verifiers before confirmation. Sources: ~90 fetched across IETF datatracker/IANA/RFC editor, kernel source and Documentation/ (including per-version bpf.h diffs), LLVM and GCC/binutils source and docs, LWN, eBPF Foundation, GitHub (bpf_conformance, uBPF, rbpf, ebpf-for-windows, prevail, aya, cilium/ebpf, p4mlir-incubator, xdsl-smt), and peer-reviewed venues (OOPSLA, PLDI, CAV, CGO, SAS, OSDI, NSDI, SIGCOMM, CCS, SETTA).
